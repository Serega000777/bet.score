# API bet.score

## Версионирование

Публичные маршруты начинаются с `/api/v1`. Несовместимые изменения выпускаются в новой major-версии. Ошибки используют единый объект с машинным `code`, сообщением и correlation id.

## Текущий контракт

`GET /api/v1/health` возвращает состояние процесса и версию API.

`GET /api/v1/ready` параллельно проверяет PostgreSQL и Redis. При готовности
возвращает `200`, а при timeout или ошибке обязательной зависимости — `503`.
Ответ содержит только безопасные статусы `ok/unavailable`, без адресов подключений
и диагностических сообщений драйверов.

Каждый ответ содержит `X-Request-ID`. Клиент может передать валидный UUID в
`X-Correlation-ID`; некорректное значение безопасно заменяется серверным UUID.

`GET /api/v1/metrics` отдаёт Prometheus-совместимые HTTP-счётчики и суммарную
длительность. Endpoint намеренно исключён из OpenAPI. В label `route` используется
шаблон маршрута, а не пользовательский URL, что ограничивает cardinality метрик.

### Каталог событий

`GET /api/v1/sports`

Возвращает виды спорта, для которых есть предстоящие события. `event_count` содержит
количество таких событий для каждого вида спорта.

`GET /api/v1/competitions`

Возвращает соревнования с предстоящими событиями. Необязательный параметр
`sport_code` ограничивает результат выбранным видом спорта. Каждый элемент содержит
канонический UUID соревнования, код вида спорта, страну и `event_count`.

`GET /api/v1/events`

Возвращает ближайшие матчи, отсортированные по времени начала. Параметры:

- `starts_from` — ISO 8601 дата и время, по умолчанию текущее время UTC;
- `limit` — от 1 до 100, по умолчанию 20;
- `sport_code` — необязательный канонический код вида спорта;
- `competition_id` — необязательный канонический UUID соревнования.

Ответ содержит `items` и фактический `count`. Каждый матч включает вид спорта, соревнование, статус, время и ровно двух участников с ролями `home` и `away`.

`GET /api/v1/events/{event_id}`

Возвращает карточку матча. Для неизвестного UUID используется HTTP 404:

```json
{
  "code": "event_not_found",
  "message": "Матч ... не найден"
}
```

`GET /api/v1/events/{event_id}/provenance`

Возвращает до 20 последних зафиксированных источников фактов матча: ключ
поставщика, версию, время наблюдения, время ingestion и SHA-256 checksum.
Публичный ответ намеренно не содержит исходный JSON payload и внешний ID
события поставщика. Для неизвестного UUID возвращается тот же HTTP 404
`event_not_found`.

### Авторизация Telegram

`POST /api/v1/auth/telegram`

Принимает необработанную строку `init_data` из `Telegram.WebApp.initData`. Backend проверяет HMAC-подпись, `auth_date` и профиль пользователя. При успехе создаётся отзывная `HttpOnly` cookie-сессия; исходный session token в БД не хранится.

`GET /api/v1/auth/me`

Возвращает текущего пользователя по cookie. Без активной сессии отвечает HTTP 401 с кодом `authentication_required`.

`DELETE /api/v1/auth/session`

Отзывает серверную сессию, очищает cookie и возвращает HTTP 204.

### Сохранённые матчи

Все маршруты требуют действующую `HttpOnly` cookie-сессию.

- `GET /api/v1/saved-events` возвращает до 100 сохранённых матчей пользователя;
- `PUT /api/v1/saved-events/{event_id}` идемпотентно сохраняет существующий матч;
- `DELETE /api/v1/saved-events/{event_id}` идемпотентно удаляет матч из сохранённых.

Данные изолированы по каноническому UUID пользователя. Неизвестный UUID матча при
сохранении возвращает `404 event_not_found`.

### LIVE-обновления

`WS /api/v1/live/events/{event_id}` передаёт версионированные уведомления:

```json
{"type":"event.updated","protocol_version":1,"event_id":"<uuid>"}
```

Handshake принимает только UUID существующего события и доверенный браузерный
`Origin` из `API_CORS_ORIGINS`. Provider payload через канал не передаётся. После
уведомления клиент перечитывает каноническое состояние через REST; при разрыве
соединения использует exponential backoff с пределом 30 секунд.

Сервер отправляет `{"type":"heartbeat","protocol_version":1}` с интервалом
`LIVE_HEARTBEAT_SECONDS`, не отменяя ожидающую Redis-подписку. Одновременно
действуют process-local лимиты `LIVE_MAX_CONNECTIONS` и
`LIVE_MAX_CONNECTIONS_PER_EVENT`; превышение отклоняется WebSocket-кодом `4429`.
Общий кластерный предел рассчитывается с учётом количества workers и реплик.

Prometheus endpoint содержит gauge `bet_score_live_connections` и counter
`bet_score_live_connection_rejections_total`. Метрики не используют UUID события
или IP клиента как labels, поэтому их cardinality ограничена.
